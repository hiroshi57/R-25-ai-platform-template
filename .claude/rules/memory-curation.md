# メモリ再編成ルール（preservation rule）

> **適用対象**: `.claude/agent-memory/`・Claude Code skills・`harness-logs/` を編集/統合/再編成する全エージェント
> **起源**: 提案 `harness-proposals/2026-09-11-filesystem-memory-findings.md`（提案1）／根拠 arXiv:2607.26637 RQ1
> **承認**: 2026-09-11 人間承認済み

## 背景

ファイルシステムベースのメモリで実証された最悪の退行は、**再編成パスが本文を黙って圧縮する
（silently condense）** こと。要約しながらの再編成は、記憶ストアを no-memory ベースライン以下に
劣化させうる。保存ルールを1つ守るだけでこれを防げる。

## ルール（MUST）

再編成 = フォルダ移動・ファイル統合・分割・見出し再構成・並べ替え を指す。

1. **本文を要約・圧縮・削除しない。** 構造だけを変え、内容は逐語（verbatim）のまま移送する。
2. **統合で重複を除く場合も情報を落とさない。** 重複行の除去は「完全に同一の情報」に限り、
   ニュアンス・日付・出典・数値が異なる行は残す。
3. **削除は明示タスクのときだけ。** 「整理」を口実に既存記憶を消さない。古い事実は上書きではなく
   `[更新: YYYY-MM-DD]` 付きの追記で更新し、経緯を残す（in-place edit）。
4. **`harness-logs/` の生ログは常に逐語保存。** 要約版で置き換えない（グローバル CLAUDE.md セクション7と整合）。

   > **補強根拠 [追加: 2026-11-11]**: arXiv:2609.11873 §6「Reproducible Infrastructure for
   > Cross-Round Inheritance」も、後継が「改善がどう得られたか（失敗した代替案・証拠が
   > 成り立つ条件を含む）」にアクセスできることを RSI 成立の要件とする。再利用アーティファクトは
   > 親状態・提案変更・動機づけ証拠・評価設定・受理判断・その後の利用を繋ぐべき、とされる。
   > 生ログを要約で置換するとこの継承が壊れる。arXiv:2603.28052 と独立に同じ結論。
   > 起源: 提案 `harness-proposals/2026-09-15-rsi-roadmap-alignment.md`（提案2）。

## セルフチェック（コミット前・MUST）

再編成コミットの前に、情報欠落が起きていないことを diff で確認する。

```bash
# 再編成対象パスを指定（例: .claude/agent-memory）
TARGET=".claude/agent-memory"
# 追加(+)より削除(-)が大幅に多い = 圧縮の疑い。中身を目視確認する
git diff --numstat HEAD -- "$TARGET"
# 削除された本文行を一覧（純粋な移動なら別ファイルに同内容が現れるはず）
git diff HEAD -- "$TARGET" | grep -E '^-' | grep -vE '^---'
```

- 削除行がある場合、その内容が**別ファイル/別見出しに逐語で再出現している**ことを確認してからコミットする。
- 再出現しない削除（＝実質的な要約・欠落）が1件でもあれば、コミットを止めて内容を復元する。

## 例外

- ユーザー/Lead が明示的に「要約して」「削除して」「作り直して」と指示した場合のみ、本ルールを外れてよい。
  その場合も何を要約/削除したかをコミットメッセージに残す。

# 整理の投資判断（提案2 / RQ2・結論）

> **承認**: 2026-09-11 人間承認済み

組織化（curation）は目的ではなく手段。実証結果では、**組織化そのものは回答品質を上げない**。
整理の確実な見返りは「**大規模ストアでの検索コスト削減**」に限られる（大規模で約半減、小規模では割に合わない）。

## ルール

1. **小規模ストアで過度なフォルダ分割・再編成をしない。** curation は per-episode で安くならない（手間が増えるだけ）。
2. **「きれいに整理したい」衝動が出たら、先に次の3レバーを見直す。** 成果を実際に動かすのはこの順:
   - (a) **書き込むエージェントの能力**（記憶を書く側のモデル/プロンプト品質）
   - (b) **記憶を提供する形式**（逐語か蒸留か。下記「記憶の提供形式」参照）
   - (c) **curate に使うツールセット**（`.claude/rules/harness-retro.md` 参照）
3. **整理の是非は「素材の大きさ」で判断する。** ストアが検索コストを実感するほど大きいときだけ、階層化に投資する。

# 記憶の提供形式（提案3 / RQ2）

> **承認**: 2026-09-11 人間承認済み

スキル/記憶をどの形で消費者（consumer エージェント）に渡すかは、**consumer の能力で最適が逆転する**。

## ルール

1. **強いエージェント向け**: 逐語の生ログ（`harness-logs/` の episode log）をそのまま参照させる。蒸留で情報を削らない。
2. **弱いエージェント向け**: 蒸留済み skill（手順化・要点化したガイダンス）を渡す。
3. **二層を両方維持する**: 生ログ層（`harness-logs/`）と蒸留層（skills）のどちらか一方に寄せない。
   片方だけにすると、逆側の consumer で性能が落ちる。
4. 逐語ログは「全部を毎回読ませる」検索コストが唯一 store と共に増える負債。大規模化したら
   蒸留層のインデックス化で検索範囲を絞る（提案2の検索経済性と整合）。
