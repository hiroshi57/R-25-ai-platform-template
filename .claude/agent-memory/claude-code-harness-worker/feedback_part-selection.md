UI Parts Design Dictionary（`C:\Users\hiroshi_takizawa\ui-parts-design-dictionary`）に
新パーツを載せるかどうかは、**「サムネイル一覧で既存と並べたとき、即座に別物と分かるか」**で判断する。
フォーマット（型）が明らかに違うものだけ採用し、**型は同じで中身の工夫レベル（微妙な違い）は採用しない。**

**Why:** ユーザーはこのツールを「今こういう見せ方／アイデアがあったんだ」というフックを得るための
サイト集として使いたい。微妙な違いは後からAIで微修正する前提なので、辞書に溜める価値が低い。
「違いがないなら削除して」「4つの違いが分からない」と繰り返し指摘されており、数を揃えることより
明確な差別化を優先する。2026-09-03 に「明らかに違うものだけを集めて。微妙な違いなどは、あとから
AIで微修正などをします」と明示された。

**How to apply:**
- 採用してよい例（型そのものが違う）: ○×機能比較マトリクス表、機能×人数の見積もり図解、
  用件分岐の窓口ボタン群、写真＋イラストを敷いた賑やかなCTA帯、扇状カードスタックのカルーセル等
- 見送るべき例（型は同じで中身が違うだけ）: 既存とほぼ同じ2カラム問い合わせフォーム（顔写真や
  代替導線が付くだけ）、4プランカードの割引訴求違い、中央寄せ2ボタンCTAのマイクロコピー違い、
  横並びメルマガバー等
- 「各カテゴリ3〜4件ずつ」のような数の目標を受けても、明確に違うものが足りなければ無理に埋めない。
- 撮影候補を評価するとき、まず既存パーツ（`data/parts.json` の同カテゴリ）を確認し、型の重複を避ける。
- **判断の但し書き（レイアウト同型だが見せ方が新しい場合）**: レイアウト(型)が既存と同じでも、
  「見せ方のアイデア」自体が明確に新しく1エントリの価値があるなら採用してよい（例: pricing-bitrix
  はカード型だが"割引・キャンペーン訴求"という別フック）。ただし色・文言だけの違いは不可。
  この場合、報告や notes で「型が明らかに違う」と過剰に言わず、「レイアウトは同型だが○○という
  別フック」と正確に書く。迷ったら見送り側に倒す。
- **自己申告の誠実さ**: 「厳選した」「型が明らかに違う」と要約するときは、採用/却下の判定が
  自分のルールと矛盾していないか（同じ理由で却下したものと同型を採用していないか）を必ず確認する。
  2026-09-03 に pricing-bitrix を採用しつつ Figma のカード型を却下した点が、skeptic レビューで
  内部矛盾として指摘された。
