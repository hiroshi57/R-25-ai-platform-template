# AI コーディング・ループの設計

ループを回す前に、人間が何を決めるかを先に決める手順。
出典は mizchi「俺のAIプログラミング手法」（Zenn, 2026-10-05）。良い点だけを本ハーネスの6層に対応づけた。
採らなかったものは末尾の「見送るもの」、出典の確度は「出典と確度」に書く。

## いつ使うか

- AI に繰り返し作業を任せる前（ループ・定期実行・`/goal` 的な運用）
- 評価指標や CI を選ぶ、または増やすとき
- ループが失敗して、次の手を決めるとき
- 実装しようとしている仕様そのものが正しいか不安なとき

## 1. 人間の役割を先に決める

| 役割 | 決めること | 6層 |
|---|---|---|
| 評価指標を作る | どの数値を改善するか。トレードオフで何を優先するか | 層1 契約（`done_when`） |
| ループを構築する | 自動化で浮いた時間を、評価指標の改善に使う | 層3・4 |
| イテレーションを評価する | AI の行動ログを見て、指標を正しく満たしているか確かめる | 層6 トレース |
| テストと CI をチューニングする | 指標が増えると CI は長くなる。優先するものと、やらないものを明記する | 層5 |
| モデルの性能を評価する | 無茶振りして限界を観察する。できたこと・できなかったことがドメイン知識になる | 層4（lessons） |

## 2. 考える順番（5ステップ）

1. **任せられる仕事か。** 任せられないなら、ブロッカーは何か。
2. **完了の定義と評価指標は何か。** 数値にできるなら自動化できる。→ 契約の `done_when` に書く。
3. **一度やらせてみる。** 設計し尽くす前に、まず振る舞いを観察する。
4. **できたら**、人間がつきっきりでなくても回せるか。判断基準そのものを作れるか。→ 証拠ゲート（`verify`）に落とす。
5. **できなかったら**、理由を分類してから直す（下の §4）。

## 3. 評価指標の選び方

- 具体的な数値に落とす。主観的な判断が要ると、人間が都度呼び出される。
- 実行のたびに揺れる値より、毎回同じ値になる指標を優先する（記事は、CI で安定しないベンチマークの代わりに「RSS や Fuel など決定的な指標」を挙げている）。
- 記事が挙げる例:
  - メモリ使用量（RSS）などの決定的な性能値（計測は hyperfine / perf / valgrind）
  - 厳しいルールでの lint warning 数
  - 循環的複雑度
  - コード重複率
  - ミューテーションテストの kill 率
  - VRT（見た目の回帰テスト）の一致率
- （補足）採用する前に、同じ入力で2回測って値が一致するかを確かめる。

## 4. 失敗の分類

| 失敗の理由（記事） | 打ち手 | 本ハーネスでの置き場所 |
|---|---|---|
| コンテキスト不足 | 指示と、守るべきテストを足す | `missing_context` |
| 権限の不足 | 与えられるか検討する | `agent-harness/tools/permissions.json`（※1） |
| 性能の不足 | プロンプトを強めない。記録して、モデルの更新を待つ（記事は「半年寝て待つ」） | `capability_limit`（※2・新規候補） |

- ※1 `missing_guardrail`（ガードを足す）と同じファイルを触るが、**向きが逆**（緩める）。緩めるときは、承認要件（`requires`）を同時に決める。
- ※2 本ハーネスの4つの型（`missing_context` / `bad_tool_contract` / `missing_guardrail` / `weak_verification`）を直しても同じ失敗が残るときの置き場所。記事の主張ではなく、本リポジトリでの解釈。

## 5. リスクでレビューの経路を分ける

記事は、安全なコードは AI がそのままマージし、危険なもの（DB スキーマ変更や terraform の変更）は人間へエスカレートする運用を紹介している。ただし原文は「OpenAI はAIがトリアージして、ある程度マージを自動化しているらしい」という伝聞で、著者自身のレビューツールも TODO の段階。

**取り入れるのは分け方だけ。** 自動マージそのものは、このスキルの対象外。

- 層0の分類器で risk を決める。high（DB スキーマ・インフラ・本番・顧客データ・送信・削除）は、必ず人間の承認に回す（層3）。
- 自分の専門外の範囲は、別の観点のレビューに回す。

## 6. 探索的に改善させる

- **視点を与える。** 誰にとって、どの数値が大事で、だからどう改善するか、までを書く。
  - 例: 「SRE視点でテレメトリを計装して」「データベースに対するN+1を見つけて潰して」「テストを壊さない範囲でリファクタリングをして」
  - 例: 「セキュリティ視点で攻撃側としてチェックリストを作り、localhostに閉じてペネトレーションして」
- 自信がないときは、Docker など適切なサンドボックスで実行する。
- 見つかったものは1つの Umbrella Issue にまとめ、上から順に処理させる。
- 本リポジトリの制約が常に優先する: 本番デプロイ禁止、秘密の隔離、high リスクの承認。記事の「丸投げ」はそのままは採らない。

## 7. 人間が理解するものを絞る

全コードを読むのは間に合わない。せめて振る舞いを把握する。

- E2E のケース名、テストコード、関数シグネチャを見る
- AI に概念的に説明させる

## 8. 形式手法を使うか（仕様が合っているかの検査）

実装しようとしている仕様が合っているか、実現できないものを作ろうとしていないか、最適化のアルゴリズムが正しいかを、強い型や論理で検査する。自然言語はそのまま形式仕様にならない。「性質を記述する」つもりで書く。

| 状況 | 道具（記事） |
|---|---|
| マイクロサービス、マルチスレッドのキャッシュ制御 | TLA+ または Quint |
| 述語論理で書ける制約 | Z3 |
| アルゴリズム自体の開発 | Lean |
| ユーザー権限まわり | Alloy |
| 迷ったら | Z3 か TLA+ |

使い方（記事の実例）:

- 形式化できる部分を形式化し、それをテストオラクルにして、実装が従っているか確かめる
- モデル検査で反例が出たら、実際のテストケースに落とす
- 何を検査したかを、ドメインの言葉を使わず例え話で説明させる

## 9. プロンプトは陳腐化する

- 「あなたは優秀なプログラマです」型の定型句は古い。
- グローバル指示には、**選択肢が複数あるときの判断基準**だけを書く（例: node は 24+、新規は npm でなく pnpm）。一般的でないこだわりや制約は AGENTS.md に書く。
- モデルの世界知識は、コンテキストに与えた情報より弱い。モデルにとって既知の情報が多い構成（よく知られた OSS）ほど、高効率で動く。

## ループを回す前のチェック

- [ ] `done_when` が数値（または機械的に判定できる条件）で書けている
- [ ] 指標が決定的か確かめた（同じ入力で2回測って一致）
- [ ] 停止条件がある（契約の `max_repairs` / `escalate_when`）
- [ ] high リスクの操作が、承認ゲート（層3）につながっている
- [ ] 失敗したときに分類する型がある（§4）

## 見送るもの

| 記事の内容 | 判断 | 理由 |
|---|---|---|
| 原始的な Ralph Loop（`while :; do claude -p ...; done`） | 見送り | 停止条件がない。本ハーネスは契約の `max_repairs` / `escalate_when` を必須にする（本リポジトリの判断） |
| `/goal`（満たすまで自律ループ） | 条件付き | 客観的な指標があるときだけ。主観判断が要ると人間が呼ばれる（記事も同じ趣旨） |
| マルチエージェント | 見送り | 記事自身が「決定的な解がない。難しいなら無理して使わなくていい」と書いている。Worker は子エージェントを起動しない（NG-3） |
| dspy / RLM | 見送り | 記事自身が「実験的な手法」と書いている。本リポジトリでは未検証 |
| `/compact` | 見送り | 記事の注意は「正しく判断基準が与えられていないと、間違ってる側に倒れる」。本ハーネスは状態を層4に外出ししている |
| AI にマージまで任せる | 見送り | 伝聞であり、承認なしのマージは範囲外（§5） |
| 外部のスキル・ツール（explainer / similarity / cccc / maintainer-persona / formal-methods-reconciler） | 依存しない | 記事内の紹介であり、未検証 |
